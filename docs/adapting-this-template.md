# 把这个模板落地到你的团队

这个仓库是一套**给非技术岗位的 Git 工作区**:文档、规范、提交检查、
交互式入门、以及给 AI 的说明。它刻意不绑定任何具体职能 ——
设计、运营、市场、HR、法务、客户成功都能用。

落地大约需要一小时,大部分时间花在想清楚「我们产出什么」上,不是花在配置上。

---

## 0. 先从模板起一个自己的仓库

这个仓库是 GitHub **模板仓库**。在它的页面上点 **Use this template → Create a new repository**,
起个属于你们团队的名字 —— 你会得到一份干净的副本,没有模板的提交历史。

(命令行:`gh repo create <你们组织>/<新名字> --template <模板仓库> --private --clone`)

**不要直接在模板仓库里干活** —— 那样每个团队的改动会互相打架。

## 1. 先决定你有哪些目录

**这是唯一真正需要动脑的一步。** 其余都是填空。

模板不预设任何工作目录 —— 因为不知道你们产出什么。问自己:
**将来找东西时,最可能按什么去找?** 按那个维度开顶层目录。

几种常见的切法:

| 按什么分 | 适合 |
|---|---|
| 职能 / 产出类型 | `budgets/` `reports/` `policies/` —— 最常见 |
| 客户 / 项目 | 工作天然按外部对象组织 |
| 时间 | 产出以周期为单位,过期的很少回头看 |
| 受众 / 用途 | 同一件事要面向不同人产出不同版本 |

**几种可以并存。** 做系统的同事会开 `code/`,做内容的会开 `content/`,
两者在一个工作区里不冲突 —— 这本来就是个 monorepo。

每个顶层目录放一个 `README.md` 说明它是什么,并在
[`AGENTS.md`](../AGENTS.md) 的「手上有什么」里留一行。
`uv run check-chain` 会检查这件事 —— 没有入口的目录,别人不会知道它存在。

> **别造「其他」。** 那是分类腐烂的起点:所有说不清的东西都往里倒,
> 最后没人敢看。出现放不进任何目录的东西,说明该加一个了。

## 2. 填掉 `[按团队填写]`

```bash
grep -rn '\[按团队填写\]' --include='*.md' .
```

主要在 `AGENTS.md` 的「干活」一节 —— 补上你们这个岗位特有的东西:
质量标准、审校流程、常见错误、要用的元信息字段。**这是最该被替换掉的一节。**

## 3. 改掉三处身份信息

| 在哪 | 改什么 |
|---|---|
| `README.md` | 标题、`gh repo clone` 的地址 |
| `AGENTS.md` 开头 | 一句话说明这是谁的工作区 |
| `pyproject.toml` | `name`(可选,改成你们仓库的名字) |

## 4. 按需要调整规范

**改之前先读 [`design-rationale.md`](design-rationale.md)** ——
每条规定当初为什么这么定、代价是什么都写在那儿。
判断那个理由在你的团队还成不成立,再决定改不改。

几个常见的调整点:

- **禁用格式**(`tools/workspace/policy.py` 的 `BLOCKED_SUFFIXES`)——
  如果你们必须和外部交换 `.xlsx`,考虑放开它,但想清楚代价。
- **体积上限**(同文件 `MAX_PLAIN_BYTES`)—— 默认 5 MB。
- **提交语言**、**分支策略** —— 见 `AGENTS.md` 的「Git」一节。

改完两件事都要做:改 `policy.py`(代码认的)**和** `AGENTS.md`(人和 AI 认的)。

## 5. 需要写工具或代码时

模板自带的工具链在 `tools/workspace/`,但**包不限一个,也不必放在 `tools/` 下** ——
服务于某块业务的代码,跟着那块业务走(`budgets/forecasting/`、`code/<系统名>/`),
只有真正跨领域通用的才放 `tools/`。

新增的包在 `pyproject.toml` 的 `packages` 里加一行,新命令在 `[project.scripts]` 里加一行,
然后 `uv sync`。写法约定见 [`tools/README.md`](../tools/README.md)。

**什么该写成工具、什么该由 AI 照约定直接做**,见 `AGENTS.md` 的「方法论 → 工具链设计」。
简单说:确定性的检查、不可逆操作的守门、需要精确重复的机械变换才值得写成工具。

## 6. 加你们自己的技能

模板只带 `improve-workspace`。**你的团队反复要做的事,应该做成技能** ——
它们是 AI 干活时的入口。

```
.codex/skills/<名字>/SKILL.md
```

```markdown
---
name: 技能名
description: 一句话说明什么时候该用它。写清楚,这决定了 AI 会不会想起来用。
---

# 标题

具体步骤、边界、注意事项。
```

`.claude/skills` 是指向 `.codex/skills` 的符号链接,写一份两边都认。

**写完加进 `AGENTS.md` 的「手上有什么」**,否则等于没做 ——
`uv run check-chain` 会检查这件事。

## 7. 验证

```bash
uv run check-env      # 环境配好了没
uv run check-chain    # 每份文档还能不能从 AGENTS.md 走到
uv run precommit      # 提交检查能不能跑
```

---

## 别做的事

**别为了让规范"更宽松"而删掉检查。** 提交检查拦的三件事
(Office 格式、超大文件未走 LFS、LFS 没装好)在任何团队都成立,
而且第三件拦的是不可逆的错误。

**别删 `.gitattributes` 里的 LFS 规则,也别把 `git lfs install` 当可选项。**
全公司统一装 Git LFS。即使你们现在只有纯文本,总有一天会有人放一张截图 ——
那时候规则不在,图片就原样进了 Git 历史,而这是清不掉的。
装 LFS 的成本是一次性的,不装的代价是不可逆的。

**别把文档改长。** 这套东西的可用性建立在「短到有人愿意读」上。
加一段之前先问有没有哪段可以删。

**别一次性配完就不管了。** 这个工作区的核心假设是**基础设施会随工作一起演进** ——
遇到摩擦就改文档、改工具、改规范。展开讲在 `AGENTS.md` 的「方法论」一节,
以及 `improve-workspace` 技能里。
