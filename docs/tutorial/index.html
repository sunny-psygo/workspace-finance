    关于 commit message

    它是写给三个月后的你和同事看的。那时候没人记得「更新」是更新了什么。

    ✅新增客户培训材料初稿(基于上周的访谈记录)
    ✅Add Q3 pricing comparison based on the product team's figures
    ❌更新 / 修改了一些东西 / final / 最终版2

    英文是更规范的默认(开发惯例,工具链也更顺), 但英语不好就写中文 —— 把事情说清楚,比用哪种语言重要得多。 憋出一句自己都不确定的英文,不如一句准确的中文。

    文件名里写「最终版」是网盘时代的习惯。Git 里每次提交都带着时间、作者和说明 —— 历史本身就是版本,不用靠文件名区分。

    2冲突

    你和同事改了同一句话,git pull 时会撞上。Git 把两版都塞进文件、标上记号,等你定夺。

    你要做的是决定留什么,然后把三行记号全删掉。 试试看:

    改完在真实仓库里是:

    git add 那个文件
git rebase --continue
git push
    处理不了就退回去,什么都不会丢: git rebase --abort
    然后找同事当面聊。一句「这段你想留哪版」能解决的事,不要跟 Git 较劲。

    怎么少遇到冲突: 动手前先 git pull,能消灭八成; 在群里说一声「我在改 XX」。图片这类二进制文件尤其要说 —— 文本冲突能手工合并,.png 的冲突无法合并,只能二选一,另一份直接没了。

    3出事了

    只要你提交过,东西就丢不了。 Git 的设计目标就是不丢数据,绝大多数「我完蛋了」一分钟内能恢复。
    不确定就先敲 git status —— 它会告诉你现在什么状态、下一步能做什么。
    想丢掉还没提交的改动
    git restore 文件名     # 单个
git restore .         # 全部
    ⚠️ 这会永久丢失未提交的内容 —— 从没提交过的东西,Git 里没有它的记录。 先 git diff 看一眼你在丢什么。

    不想丢、只是想先放一边:git stash,回头 git stash pop 拿回来。
    想找回以前的版本
    git log --oneline -- 文件路径              # 这个文件的历史
git show <提交号>:文件路径                  # 那时候长什么样
git restore --source=<提交号> -- 文件路径   # 恢复到那个版本
    <提交号> 是 git log 里那串七位字符。恢复不会丢掉现在的版本 —— 它也在历史里。
    push 被拒绝了
    ! [rejected] main -> main (fetch first)
    GitHub 上有你还没有的提交(同事推过东西了)。 
    git pull
git push
    git pull 如果报冲突,回到上一节。
    提交错了,想撤销
    还没 push: 
    git reset --soft HEAD~1    # 撤销提交,保留改动(最常用)
git reset --hard HEAD~1    # 撤销提交,并丢弃改动 ⚠️
    已经 push 了 —— 用一次新提交抵消它: 
    git revert <提交号>
git push
    已推送的一律用 revert,不要用 reset。 reset 会让你的历史和同事的对不上,后果比原来的错误麻烦得多。

    message 写错了、还没 push:git commit --amend -m "新的"。 已经 push 了就算了 —— 改它的代价大于一条不完美的 message。
    提交被检查拦住了
    看到 ✗ 提交被拦截,报错里已经写清了原因和解决办法,完整读一遍。 三种情况:Office 格式(转成 .md / .csv)、 超过 5 MB 没走 LFS(说明这个扩展名还没交给 LFS,补进 .gitattributes)、 LFS 没装好(git lfs install)。

    第三种最值得重视 —— 它帮你拦下的是一个不可逆的错误。

    确属合理例外的,git commit --no-verify 跳过,但你要能解释理由。
    把大文件或密码提交上去了
    还没 push: git reset --soft HEAD~1,把文件挪出去或加进 .gitignore,重新提交。

    已经 push 了:立刻停手,找技术同事。 不要自己试命令,那通常只会让情况更糟。

    密钥泄露的话,除了清理历史,必须立刻作废并更换那个密钥 —— 假设它已经泄露了,公开仓库会被自动扫描,通常在几分钟内。
    文件名显示成 \344\270\255 这样的乱码
    git config --global core.quotepath false
git config --global core.precomposeunicode true
    根本的解法是别用中文文件名。 我们的约定是文件名一律 ASCII, 中文写在文件内容里,不写进文件名 —— 见 AGENTS.md。 别人交给你的文件如果是中文名,不必强行改 —— 改名会打断对方的引用。
    屏幕突然变成一个奇怪的编辑器
    Git 打开了 Vim。一堆 ~,打字没反应,关不掉。

    保存退出:Esc → :wq → 回车ㅤ|ㅤ 放弃退出:Esc → :q! → 回车

    换掉它:git config --global core.editor nano
    (顺带,git commit 加 -m "..." 就不会弹编辑器。)
    完全看不懂的报错
    1. 先 git status
    2. 把报错原样交给 AI —— 不要复述、不要概括,整段复制, 并说明你刚执行了什么、想做什么。这正是值得交给 AI 的那类事。
    3. 还不行就找同事,带上:执行的命令、完整报错、git status 输出。

    在此期间不要乱试命令。 一个能救的局面,常常是被后面几条「试试看」搞成不能救的。 停下来问,不丢人。

    绝对不要做

    git push --force覆盖 GitHub 上的历史,同事的工作可能直接消失。 本仓库任何情况都不需要它。
    对已推送的提交 reset --hard你的历史和同事的对不上,之后每次 pull 都是灾难。用 revert。
    rm -rf .git删掉整个版本历史。
    复制粘贴看不懂的命令网上搜到的「一行解决」经常带 --force。看不懂就别执行。
    把 <<<<<<< 提交上去它会跟着内容一起交出去,而且通常没人发现,直到对方看到。

    4存成什么格式

    能用纯文本表达的,就用纯文本。 不是技术洁癖,是三件实打实的事:

    AI 读不了二进制。 我们的工作方式建立在「AI 能接手你的产出」之上 —— 它能读 Markdown、能基于它改写对比;面对 .docx 它拿到的是一坨压缩过的字节。

    版本历史会失效。 .docx 是压缩包,改一个字整个文件的字节全变。 Git 只能说「这个文件变了」,说不出变了什么 —— 那用 Git 就没意义了。纯文本则是这样:

    - 我们建议把迁移推迟到明年。
+ 我们建议在 Q4 之前完成迁移。

    两个人同时改不会打架。 各改各的段落,Git 自动合并,你甚至不会察觉。 换成 .docx,必然冲突且无解,总有一个人的活白干。

    要做的事用
    文章、方案、纪要、脚本.md
    表格数据.csv(要算就配个 .py)
    幻灯片Marp / Slidev(用 Markdown 写)
    流程图、架构图Mermaid(写在 .md 里,GitHub 直接渲染)
    图标、简单图形.svg
    对外交付的定稿.pdf(导出产物,源文件仍是 .md)

    .docx .xlsx .pptx .pages .numbers .key 提交时会被拦截。理由和例外见 design-rationale.md。

    这类天然是二进制,没得选 —— 走 LFS,正常 git add 即可。 公司用付费方案,图片原样提交就行,不用压缩,仓库到几个 GB 没关系。

    5什么自己做,什么交给 AI

    不是「简单的自己做,复杂的交出去」。真正的标准是 「熟练的开发者遇到这一步,会不会选择自己来」。

    谁来什么
    你自己 git commit git push —— 够重要,又足够简单。 这是你对「什么时候存档、什么时候发出去」的判断,不该外包。
    AI 直接做 ls cat grep 这类它干活本来就要用的 —— 不用你批准,那只会拖慢它。
    AI 先问你 brew install apt install、动系统 Python 的操作 —— 这些改的是你的电脑,不是这个仓库。它应该先说清楚装什么、为什么。
    交给 AI 从素材写稿、跨平台改写、解释看不懂的报错、把重复劳动写成脚本、 理清一次复杂的冲突或回退。

    界线会随着你变熟练而移动 —— 今天需要问的,下个月你自己就会了。主动往上挪。

    两个方向都要防:把所有操作都外包出去的人, 遇到第一个 AI 也搞不定的场景就卡死了;但凡事都要点头确认, 又会把一个能自己干活的 AI 变成很慢的工具。

    仓库里已经有现成技能,在 claude 或 codex 里输入 / 就能看到: /draft-from-raw(从素材写稿)、/improve-workspace(改进这套工具)。

    它会顶你,这是故意的

    你让 AI「就让我把这个 docx 提交了吧」,它多半不会照做, 而是先告诉你为什么不该这么干,然后帮你把文件转成 Markdown。

    这不是它出毛病了,是它被要求这么做的。 这些规矩存在是有原因的 —— 每一条的理由和代价都写在 design-rationale.md 里,你可以去核对。 一个对什么都点头的 AI,会在几个月里把这套工作方式悄悄变回从前那样。

    但它也不该拦着你不放。听完理由你仍然坚持、并且说得出为什么, 它就该照办 —— 你是成年人,可能知道它不知道的情况。 真觉得某条规矩错了,那就去改它,理由写进 design-rationale.md。 破一次例和改掉规矩是两回事,别把前者当成后者。

    6不用排队:同时做几件事

    常见的一幕:你让 AI 做一件事,盯着它跑完,再让它做下一件 —— 但这两件事根本不相关,你为什么要等?

    worktree 就是解决这个的:同一个仓库,再开一个独立的工作目录。 两个目录互不干扰,你可以在每个里面各开一个 AI 会话,让它们同时干,你在中间巡视。

    git worktree add ../ws-预算 -b 预算    # 新建一个工作目录
cd ../ws-预算                          # 进去，在这里开新的 AI 会话
git worktree list                      # 看看现在有哪些
git worktree remove ../ws-预算          # 干完了，删掉

    本仓库里 worktree 开箱即用 —— 提交检查、LFS、Git 配置都自动继承, 工具环境第一次运行时自己装好(一秒左右)。不用重新配任何东西。

    一条要守的规矩:当天合回来

    我们要所有人都对着同一个最新状态干活。 worktree 会带一个分支(git 的要求),但它应该是短命的 —— 当天干完就合回 main、删掉。 
    git checkout main
git merge 预算
git branch -d 预算

    为什么:分叉三天再合,那部分现实已经变了 —— 而且分叉越久合并越痛,越痛越想拖,是个恶性循环。 判断标准不是「用没用分支」,而是你离主线多久了。

    AI 应该会主动提醒你这件事 —— 你连着交代两件不相关的活时, 它该建议你开 worktree,而不是让你排队。它没提,你可以问它。
