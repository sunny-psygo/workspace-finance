# 为什么这样设计

非显而易见的设定,记下当初的理由和代价。

**觉得某条设定别扭时先看这里** —— 可能它过时了(那就改),
也可能它挡下过你还没见过的坑。推翻其中任何一条,在下面追加一段:
写**理由和代价**,别只写结论(结论看仓库就知道,理由才是给下一个人的)。

---

## 所有人对着同一个前沿

**默认直接在 `main` 上提交推送,不走 PR。**

真正要保证的不是"少学两个概念",是**每个人都在同一个最新状态上干活**。
大型 monorepo(Google 的 Piper 是典型)就是这么做的:没有长期分叉,
所有改动持续汇入主干。

分叉的代价不是多了个概念,而是:

- 你基于三天前的状态干活,合回来时那部分现实已经变了;
- 分叉越久合并越痛,而痛会让人更想拖延合并 —— 这是个正反馈;
- 别人看不到你在做什么,重复劳动和冲突都在暗处积累。

PR 是评审关卡,它天然鼓励「攒一批再合」,和上面这条冲突,所以不用。

**worktree 用的分支不违反这条。** 并行干活时 git 不允许两个工作目录检出同一分支,
所以必须配一个 —— 但它是本地的、当天就合回来的,**制造的是并行,不是分叉**。

所以判断标准不是「用没用分支」,而是**你的工作偏离主线多久了**。
超过一天没合回来,就该问问为什么。

**代价是真实的:** 没有 PR 这层缓冲,冲突会直接撞到你脸上,
所以「先 pull 再动手」格外重要;也没有强制评审,
质量靠交付前的人工审核保证,不靠 Git 流程保证。

## 备选方案

- **全流程 PR** —— 鼓励攒批次,正是要避免的分叉。
- **长命功能分支** —— 同上,而且更糟:它看起来"标准",所以没人会觉得不对。

## 仓库里不放 Office 格式

`.docx` / `.xlsx` / `.pptx` 一律不进仓库,提交时会被拦截。

三个理由,按重要性:

1. **AI 读不了。** 公司的工作方式建立在「AI 能接手你的产出」之上。
   AI 面对 `.docx` 拿到的是一坨二进制,整套方式就失效了。
2. **版本历史会失效。** docx 是压缩包,改一个字整个文件的字节全变。
   Git 只能说「变了」,说不出「变了什么」—— 那用 Git 就没意义了。
3. **无法合并。** 两个人同时改一份 docx 必然冲突且无解,总有一个人的活白干。

**这是少数几条做成强制拦截的规则之一。** 理由是软约束在这件事上试过,
没人遵守 —— 而它的后果是整个协作方式的地基塌掉。

**代价:** 学 Markdown 要花时间;精细排版能力确实变弱
(但最终交付往往要在别的工具里重新排一遍,Word 排版本来也要重做);
和外部协作方有摩擦,对方发来的 docx 要先转一道。

确实必须原样存档的文件(比如合同扫描件),`git commit --no-verify` 跳过,
在旁边放个 `.md` 说明理由。**这个后门是故意留的** ——
与其让人偷偷绕过,不如让绕过成为一个需要解释的动作。

---

## 二进制素材走 LFS,仓库大到几个 GB 没关系

**为什么不斤斤计较体积:** 这个仓库要替代的是共享盘和飞书/企业微信 ——
在那些工具里没人会先压图再上传。既然用了付费 LFS,就不该把免费额度时代的
紧张感带进来。**图片原样提交,不要压缩;素材和文档共享同一套版本历史本身就是价值。**

真正不该进来的只有**大到本来就只该留在本地的东西**:相机原片、
长时间屏幕录制、多轨工程文件。这些放云盘,仓库里留个 `.md` 记链接。

**每个人都要装 Git LFS,这不是可选项** —— 哪怕你们团队现在只产出纯文本。
总有一天会有人放一张截图,那时候如果这台机器没装 LFS,图片就原样进了历史。
装的成本是一次性的,不装的代价是不可逆的。

**「超过 5 MB 且没走 LFS」会被拦截。** 这条和容量无关,和**不可逆**有关:
文件一旦绕过 LFS 进了 Git 历史就永久留在里面,即使之后删掉,
每个人克隆时还是要下载一遍;清理要重写整个仓库历史,影响所有人。

**最隐蔽的坑:** 没执行过 `git lfs install` 的机器上,LFS 规则会**静默失效**,
文件被原样写进历史而且不报任何错。提交检查专门有一项在防这个。

## AI 和人读同一份文档

`AGENTS.md` 是唯一事实来源,`CLAUDE.md` 是指向它的符号链接(不是副本)。
技能放在 `.codex/skills/`(团队多数人用 Codex),`.claude/skills` 符号链接过去。

两份内容一样的文件,一定会在某次修改后不一致 —— 这不是可能性问题,是时间问题。
一旦不一致,不同的 AI 就会拿到不同的规范,而你找不到原因。
符号链接从物理上消除了这种可能:硬盘上只有一个文件。

**需要同一份内容出现在两个位置时,用符号链接,不要复制粘贴。**

**代价:** Windows 对符号链接支持不好(公司不用 Windows,暂时不是问题);
在 GitHub 网页上点开 `CLAUDE.md` 看到的是一个链接而不是内容,会让人困惑一下。

---

## 规范写在 Markdown,HTML 只做练习

大段文字对人是反人性的,所以有了 `docs/tutorial/` 里的交互式教程。
但**规则不能只写在 HTML 里** —— AI 读 HTML 很吃力,
一旦某条规则只存在于教程里,AI 就永远不知道它。

所以按内容类型分工,不按受众分:**Markdown 承载「是什么」,HTML 承载「怎么练」。**
交互、模拟、可视化本来也塞不进 Markdown,不存在重复的问题。

两边冲突时以 Markdown 为准。教程里可以复述规则(教学需要上下文),
但要链接回对应的 Markdown。

## 工具用 Python,不用 shell

`tools/` 下一律 Python,仓库是个 uv 项目(`pyproject.toml` + `uv sync` + `uv run`)。

shell 写超过二十行就开始难读,而且要绕开一堆平台差异:macOS 自带 bash 3.2
(没有关联数组、`${var^^}`、`mapfile`),BSD 与 GNU 的 `sed -i`、`stat`、`date`
参数还不兼容。这些精力花在业务逻辑上更划算。Python 也更适合工具链长大之后的维护。

**例外是 `.githooks/pre-commit`:只用标准库,不依赖 uv。**
git 直接执行它,那一刻虚拟环境不一定就绪;它还得能在 macOS 自带的 Python 3.9 上跑。

**代价:** 多一个 `uv sync` 步骤,和一个要维护的 `pyproject.toml` / `uv.lock`;
目前没有第三方依赖,`uv sync` 基本是空操作 —— 保留 uv 项目结构是为了
将来加依赖时不用重来一遍。

## 提交邮箱用个人邮箱

公司没有统一邮箱,每个人用自己的邮箱注册 GitHub,`git config user.email`
就填那个 —— 提交记录反映真实身份。

`workspace` 会在 `gh` 已登录时顺带核对:如果 `user.email` 不在你
GitHub 账号的邮箱列表里,提交不会关联到你的头像和主页。这是个软提醒,不阻断。

## `.githooks/` 里为什么有 git-lfs 的钩子

`core.hooksPath = .githooks` 会让 git 忽略 `.git/hooks/` —— **git-lfs 的钩子也在那里。**
所以 `git lfs install` 会把它们写进 `.githooks/`,这四个文件因此跟着仓库走:
`pre-push` `post-checkout` `post-merge` `post-commit`。

**不要删。** 其中 `pre-push` 才是真正把 LFS 内容上传到服务器的那个 ——
少了它,`git push` 只推上去指针、不推文件,别人拉下来是一堆空壳,
而且推的当时不会报错。`uv run check-env` 会检查这四个是否齐全。

它们是 git-lfs 生成的 shell 脚本,不是我们的工具,原样保留即可
(我们自己的工具用 Python,那条规矩不适用于这里)。

## commit message 中英文都行

推荐英文:开发惯例,工具链、搜索、跟外部协作都更顺。
但**不强制** —— 团队里多数是非技术岗位,英语水平参差,
硬性要求英文的结果是大家憋出一堆语焉不详的短句,那比中文糟得多。

**真正的标准是「说清楚做了什么」,语言是次要的。**
所以两种都收,只拦「更新」「fix」这类等于没说的 message ——
而这条靠人和 AI 的判断,没做成检查。

## 为什么没有「新建条目」这类脚手架工具

曾经有个脚本,一条命令生成目录和文件骨架。删掉了。

**不同工作的结构本来就不一样** —— 一份报告、一个季度归档、一套政策文件、
一个小工具,长相各不相同。
把它固化成脚本,等于拿一个僵硬的模板去套所有内容;而真正的使用者是 AI,
它照着 `AGENTS.md` 的约定生成,还能按这次的实际需要调整。
写成脚本反而把它降级成了模板填空。

**由此得到的一般原则**(写进了 `AGENTS.md`):工具只做**确定性的检查**、
**不可逆操作的守门**、**需要精确重复的机械变换**。
结构性的、每次都不一样的工作交给 AI 按约定做。

目标是一组小而正交、能自由组合的工具,不是一个功能越堆越多的平台。
**每加一个功能先问:它是不是在把本来灵活的东西固化成僵硬的?**

## 注意力链条为什么是独立命令,不进提交检查

`uv run check-chain` 从 `AGENTS.md` 出发,沿文档之间的相互提及遍历,
报出走不到的文档 —— 没人指向的东西等于不存在,而这种腐烂不会报错。
它做成独立命令,没有放进 `pre-commit`。

**因为断掉的指针是可逆的。** 按「只有代价不可逆才值得强制」那条,
它够不上拦提交:发现晚一点,补一句话就修好了,不像大文件进历史那样清不掉。
拦提交的代价反而更大 —— 写了半截的文档、临时的笔记都会被挡下来。

**代价是没人会想起来跑它。** 所以它挂在两个地方:`AGENTS.md` 的命令表,
以及 `improve-workspace` 技能的「改完」一节 —— 动过文档结构的 AI 会走到那里。
一个防链条腐烂的工具,自己也必须在链条上。
