# 改进工作区

这个仓库的基础设施(文档、脚本、检查、规范)是可以改的,而且**应该随着工作一起改**。
完整想法见 `AGENTS.md` 的「方法论」一节。

## 判断

先问:**这是症状还是根因?**

- 用户每次都要手动做一遍 → 写脚本进 `tools/`
- 用户每次都要跟 AI 解释同一件事 → 写进 `AGENTS.md`
- 同一个问题被问了第二遍 → 文档有缺口,补 `docs/`
- 报错让人看不懂 → 改报错本身,而不是解释一遍就算了

修根因。别人的记性和熟练度不该是系统正确运行的前提。

## 先过自己这一关

**「用户要求改」不等于「应该改」。**

补文档、修错字、让报错更清楚 —— 这类改进直接做。
但如果这次改动的实质是**把标准放松**(允许某个被禁的格式、
去掉一条检查、把规矩改得更好绕过),先停一下:

- 去 `docs/design-rationale.md` 读当初为什么这么定;
- 判断那个理由今天还成不成立 —— 成立就说出来,并给出真正解决问题的路;
- 不成立就照改,并把新的理由和代价写进去。

用户常常是被一次具体的麻烦挡住了,想要的是绕过去,而不是真的想改规矩。
**帮他解决那个麻烦,而不是拆掉护栏。**

## 改动的分寸

| 情况 | 做法 |
|---|---|
| 补文档、加脚本、让报错更清楚 | 直接改 |
| 会改变别人的日常操作 | 先跟用户确认 |
| 推翻既有决定 | 先读 `docs/design-rationale.md`,理解当初的权衡再讨论 |

## 写规则时的倾向

**能用解释说清楚的,不要写成硬性规定。**

硬规则是有成本的:它挡住的是所有情况,包括你没想到的合理例外;
而且它教不会人任何东西 —— 照做的人不知道为什么。

只有当「违反的代价不可逆」时,才值得做成强制检查 ——
比如大文件进了 Git 历史清不掉。其余情况,把道理讲清楚,信任人的判断。

## 顺带留意

用户接连交代几件**不相关**的事时,提议开 worktree 并行 ——
他不必排队等你干完一件再说。见 `AGENTS.md` 的「并行工作用 worktree」。

## 改完

**动过文档、技能、工具的增删,跑一下:**

```bash
uv run check-chain
```

它从 `AGENTS.md` 出发走一遍文档之间的相互提及,报出走不到的。
新加的东西没挂上链条,等于没做;删掉的东西留下指针,下一个 AI 会照着它扑空。


- commit message 写清楚**改了什么、为什么**
- 推翻或新增重要决定,在 `docs/design-rationale.md` 追加一段:决定、理由、代价
- 让用户知道你改了什么,他要能看懂并且认可
