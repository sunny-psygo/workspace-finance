# 先确认那个限制是真的

**在为「做不到 X」设计变通方案之前，先确认它是不是真的做不到。**

## 怎么做

**先说出你的依据**，看它属于哪一种：

- 读过文档的某一段 → 可以往下走。
- 自己试过，见到了具体的报错 → 可以往下走。
- **「印象里不行」「一般来说不支持」→ 先去查，再动手。**

查证的顺序：翻官方文档 → 直接跑一个最小例子试一次 → 问知道的人。
**这一步通常只要几分钟。**

查完仍然不确定，就按假设继续，但**把假设显式写下来**——
写在 PR 描述里或者那段代码旁边，讲清「如果 X 其实是支持的，这段就该删掉」。

## 效果

**变通方案是永久负债。** 它一旦建成就会被后面的东西依赖，
再想拆掉的成本远大于当初造它的成本。
而如果那个限制根本不存在，你写的东西从第一行起就是多余的——
**你不是解决了一个问题，是给仓库添了一个永远要维护的东西**
（见[代码是什么](../principles/what-is-code.md)）。

几分钟的查证，对上的是长期的维护成本。这个比价永远划算。

**对 AI 尤其重要**：你对工具、平台、框架的「印象」来自训练数据，
它可能过时，也可能本来就是错的，而你不会因此感到不确定——
**这正是最危险的地方**（见[认知](../principles/cognition.md)：
最危险的状态不是信息不足，而是信息不足却不自知）。

## 反效果与边界

- **会诱发无限调研。** 查一轮就够；查不到就带着显式假设往前走，
  别把它变成一个前置研究项目。
- **救火时先绕过**，但把假设记下来，事后回来验证。
- **「限制是真的」不等于「变通方案是对的」。**
  确认之后还要再问一句：这个限制之所以硌得慌，
  是不是说明我们的抽象本来就选错了（见[深挖本质问题](../principles/dig-to-the-root.md)）？

出自[认知](../principles/cognition.md)和[代码是什么](../principles/what-is-code.md)。
